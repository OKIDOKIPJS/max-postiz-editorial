# Четыре платформы: отдельная копия и проверяемая отправка

Состояние на 31 октября 2026 года. Доработка находится в отдельной копии:
исходный checkout, его сервер, очереди, профили браузеров и история не меняются.
Наличие адаптера и успешные локальные проверки не означают живую доставку.

Список адресатов и параметры транспорта задаёт
`config/four_platform.publishing.example.json`. При инициализации он копируется
в игнорируемый `config/publishing.json`. Все четыре адресата в примере выключены,
созданные адресаты остаются на паузе; `tasks` пуст. Реальные значения заполняет
владелец только в локальных файлах копии. Токены и DSN находятся в её
игнорируемом `.env.local`, cookies — в её собственных браузерных профилях.

## Как проходит публикация

Сохранённый `Variant` содержит точную версию текста, вложений, источников и
адресата. `preflight` проверяет качество и локальные файлы без отправки.
Согласование привязывает версию, `content_hash`, адресата и будущую дату к
`Dispatch`. Обработчик отправляет только согласованный материал, повторно
проверяя его неизменность и право владения отправкой перед внешними действиями.
Telegram и VK API получают свежую проверку approval/lease через отдельный
callback перед каждым изменяющим шагом. Потеря права, пауза или отзыв
согласования останавливают следующий шаг, а не разрешают допубликовать остаток.

`sending` и `unknown` не являются разрешением повторить запрос. Lease,
сохранённые claims и журналы шагов переживают перезапуск. Сверка читает уже
созданный результат и не вызывает новую загрузку изображения или отправку.
Изменение текста, вложений, даты или адресата требует нового точного согласования.
Пауза сохраняет историю и доказательства.

| Платформа | Маршрут | Что реализовано | Граница доказательства |
| --- | --- | --- | --- |
| MAX | `max_browser` | Прежний браузерный transport, собственный профиль копии, проверка разрешённого канала и результата | Новый вход и публикация из профиля копии требуют отдельной живой приёмки; история рабочего MAX ничего не подтверждает за эту копию |
| Telegram | `telegram_api` | Bot API, текст и JPG/PNG, настоящее жирное начертание заголовка, durable шаги | Квитанция Bot API сохраняется с `verified=False`; это не независимое чтение сообщения |
| ВКонтакте, выбранная личная страница | `vk_browser` | Отдельный браузерный профиль и DOM-контракт собственной стены; подготовка и exact сверка | До приёмки отдельного профиля и живой отправки адресат выключен; наблюдение встроенного браузера не заменяет эту проверку |
| ВКонтакте, отдельный вариант сообщества | `vk_api` | Пользовательский OAuth, текст и JPG/PNG, загрузка фото, `wall.post`, отдельный `wall.getById` | Отрицательный ID сообщества; exact owner/text/attachments. Это не поддержка личной страницы новым VK ID token; fixtures всегда имеют `verified=False` |
| Пикабу | `pikabu_browser` | Автоматическое заполнение, проверки до клика, один отправляющий клик и независимый reload реализованы и проверены на локальных fixtures | Наблюдались вход и пустой редактор; offline DOM/preview не подтверждают живую отправку. Приёмка DOM/text/media продолжается |

На текущем срезе в отдельной копии Telegram inspect подтвердил
`canPublish=true` для созданного бота и закрытого канала через явно выбранный
локальный proxy. Это только доступ: посты не отправлялись. В VK вход и редактор
подтверждены только во встроенном браузере; подготовленный частный черновик
закрыт без сохранения. Вход в отдельный профиль отправителя копии ещё не
подтверждён, согласование владельца ожидается. В Пикабу наблюдались вход и пустой редактор, без живой
отправки. Доступ к аккаунту и наблюдение интерфейса не разрешают публикацию.

Почасовая автоматическая политика научного MAX сохраняет отдельные правила,
рубрики, интервал и доказательства. Она не даёт согласования Telegram, VK или
Пикабу. Reddit этим набором изменений не включается. Проверки прав, качества,
чисел, ссылок и всей истории дублей не отменяются.

## Подготовка копии

Команды ниже выполняются из корня **новой копии**, с её собственным `.venv`.
Значения в угловых скобках необходимо заменить локально; это не действующие
адресаты или учётные данные.

После чистой распаковки source ZIP сначала создайте окружение Python 3.12
и установите пакет с браузерными и тестовыми зависимостями. В уже подготовленной
копии это выполнено; повторная установка для просмотра состояния не нужна.
В браузерных примерах выбран установленный Google Chrome; его профиль создаётся
заново внутри `data` копии, авторизация не входит в архив.

```powershell
Set-Location '<ПУТЬ_К_РАСПАКОВАННЫМ_ИСХОДНИКАМ>'
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev,browser]'
```

```powershell
Set-Location '<ПУТЬ_К_КОПИИ>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . init --source-root '<ПУТЬ_К_ИСХОДНОМУ_ПРОЕКТУ>'
.\scripts\start-four-platform.ps1
```

`init` нужен только новой неинициализированной копии. Он создаёт marker
`data/four-platform/isolation.json`, локальную конфигурацию, собственные секреты
панели и выключенные источники; OpenCode и MAX остаются в `fake`. Начальная
SQLite предназначена для изолированной локальной подготовки. Для собственного
runtime PostgreSQL используется отдельная БД ниже. Повторный `init` поверх
существующего `config/app.json` отклоняется.

`routes_cli` перед чтением dotenv проверяет marker и отсутствие ссылок на чужие
`data`, `config`, `.env.local`, файлы SQLite и профили. Затем ограждение разрешает
только PostgreSQL на loopback `55448` и собственный публичный Postiz на loopback
`14007`. Пользовательские имена env из конфигурации также проверяются.
`MAX_EXISTING_BROWSER_PROFILE` запрещён: рабочий профиль не копируется и не
подключается к тестовой копии.

### PostgreSQL в Windows

Бинарники PostgreSQL должны находиться в локальном `data/tools/pgsql/bin` этой
копии. Helper ничего не скачивает и не создаёт службу Windows. При кириллице
в пути используется новый ASCII junction, указывающий **только на `data` копии**.
Не используйте уже занятый junction или путь рабочего проекта.

```powershell
# Создать один раз, после проверки полного пути текущей копии.
New-Item -ItemType Junction -Path '<НОВЫЙ_ASCII_ПУТЬ>' -Target (Join-Path (Get-Location).Path 'data')
.\.venv\Scripts\python.exe scripts/local_postgres.py start --port 55448 --runtime-root '<НОВЫЙ_ASCII_ПУТЬ>'
.\.venv\Scripts\python.exe scripts/local_postgres.py status --port 55448 --runtime-root '<НОВЫЙ_ASCII_ПУТЬ>'
```

Helper проверяет конечный путь junction. Он создаёт собственный кластер,
`editorial_hub` и `editorial_hub_tests`, сохраняет пароль в игнорируемом
`data/postgres-access.json`, а оба DSN — в `.env.local`, без вывода значений.
Для runtime после подготовки PostgreSQL можно явно установить
`require_postgresql=true` в локальном `config/app.json`. Порт `55448` указывать
обязательно: прежний порт helper по умолчанию не подходит ограждению копии.

## Настройка адресатов

Рабочий файл — `config/publishing.json`; пример остаётся безопасным и
выключенным. Укажите существующий `profile_id`, назначение `destination` и
необходимые `options`, затем отдельно разрешите нужного адресата. Скрипты не
включают его, не снимают паузу и не одобряют текст вместо владельца.

Для MAX установите `max.adapter_mode="browser"` в локальном `config/app.json`.
В `max.browser.channels` внесите точную пару «числовой ID → имя разрешённого
канала». Профиль `data/max-browser` должен принадлежать копии. Вход выполняется
командой `login max_test`; наличие окна входа или cookies не является доставкой.

Для Telegram задайте `options.adapter_mode="live"` и имя `token_env`; сам токен
сохраните в `.env.local` локальной командой `set-token telegram_test` ниже.
Боту нужны права публикации в назначенном канале.
Пример выбирает `media_layout="auto"`: короткая подпись отправляется с фото,
длинный текст до 4096 UTF-16 единиц — отдельным сообщением после фото. Оба шага
заранее записываются в durable journal. Это один согласованный материал с двумя
сообщениями, а не две независимо согласованные публикации. `atomic` запрещает
разделение при превышении лимита подписи; `photo_then_text` задаёт его явно.
Неизвестный шаг не повторяется. `reconcile` может восстановить полностью
завершённую API-квитанцию из журнала, но не повышает её до независимой проверки.

Для API-маршрута VK нужен допустимый пользовательский OAuth token с `wall`/`photos` и правами
редактора/администратора сообщества. Обычный токен сообщества нельзя считать
равнозначным этому контракту. `destination` — отрицательный числовой ID
сообщества; `options.token_env` указывает только имя env. Используется
официальная [схема VKCOM API `5.199`](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json),
версия задаётся явно в options.
Заголовок в записи стены остаётся обычным текстом: transport не обещает
неподдерживаемое жирное начертание. Загрузка, сохранение фото и отправка
имеют отдельные durable стадии. При потере финализации БД известный post ID
восстанавливается из журнала exact версии, затем читается `wall.getById`.

Это условие совместимости, а не обещание получить такой token для любого нового
приложения. Успешный вход через VK ID не гарантирует право `wall.post` и загрузки
медиа: в [issue Postiz #1408](https://github.com/gitroomhq/postiz-app/issues/1408)
описаны несовместимость профиля токена и ложные статусы публикации. Это отчёт
пользователей интеграции, а не разрешение доступа от VK. Не используйте чужие
legacy app IDs, сторонние генераторы token или обход ограничений.

По выбору владельца для личной страницы основной пример четырёх платформ
уже использует `vk_browser`. Отдельный `config/vk_browser.target.example.json`
позволяет заменить одну прежнюю API-запись `vk_test`; не добавляйте второй адресат
с тем же ID и не включайте оба маршрута ради обхода неизвестной отправки.
У `vk_browser` собственный `data/vk-browser`, положительный `options.owner`
(числовой ID владельца, заданный строкой) и `dom_contract_verified=false` по умолчанию.
`destination` — положительная собственная стена либо отрицательное сообщество
при проверенном праве публикации. Вход выполняется `login vk_test` в новом
профиле копии; cookies in-app browser и чужие сессии не переносятся. Эта ветвь
не требует предположения о совместимости нового VK ID token с API, но требует
полной собственной DOM-приёмки и явного поручения на действия в аккаунте.

Для Пикабу укажите локально `options.owner`, собственный `profile_dir` и
соответствующий ему `destination`. Тексты, теги и SHA изображений входят в
проверяемый план. Подготовлены операции `login`, read-only inspect/probe,
автоматическое заполнение и публикация через браузер. На локальных fixtures
проверена цепочка до reload и сверки. В реальном авторизованном редакторе
найдены account/title/body/tags_input/publish; отдельно offline наблюдались
структура тегов и локальный blob-preview. Это наблюдение DOM, а не приёмка
живого текстового или image-потока. До приёмки точных tag values, загруженного
изображения и отсутствия случайного сообщества сохраняйте
`dom_contract_verified=false` и адресат выключенным. Нельзя превращать
результат inspect/probe в это разрешение автоматически. Обход CAPTCHA,
изменение чужой сессии и повтор неизвестного клика не предусмотрены.

OAuth-приложения, токены и действия в аккаунтах требуют отдельного прямого
поручения владельца. Данный документ и запуск проверок их не создают.

## Команды владельца

```powershell
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . status
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . set-token '<API_TARGET_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . inspect '<TARGET_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . login '<BROWSER_TARGET_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . variants '<DRAFT_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . create-original '<DIRECT_TARGET_ID>' --file 'data/original-input.json' --attest-original
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . preflight '<VARIANT_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . resume '<TARGET_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . approve '<VARIANT_ID>' --revision <REVISION> --content-hash '<EXACT_HASH>' --at '<БУДУЩАЯ_ISO_ДАТА+03:00>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . dispatch-once
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . reconcile '<DISPATCH_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . evidence '<DISPATCH_ID>'
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . pause '<TARGET_ID>'
```

`status` показывает конфигурацию и историю, не проверяя сеть. `inspect` обращается
к назначенной площадке только для проверки доступа; `login` применим к
браузерным MAX/VK/Пикабу и открывает собственный профиль. `preflight` не отправляет
пост. `approve` сохраняет точную версию и дату, но не публикует её немедленно.
Для обычного адресата перед согласованием требуется отдельное `resume`;
`enabled=false` таким способом не меняется. Если в БД существует общая пауза
редакции, она также сохраняется: снятие паузы адресата её не отменяет.

`set-token` применим только к `telegram_api` и `vk_api`. Запускайте его в
собственном интерактивном терминале: `getpass` принимает скрытый ввод, а токен
не указывается аргументом, не передаётся через pipe и не вставляется в чат или
логи. Команда сохраняет секрет только в игнорируемом `.env.local` копии,
ставит адресат на паузу и сообщает необходимость перезапуска её обработчика.
`sending`/`unknown` и активный mutation lease блокируют смену; сначала требуется
сверка, без повторной отправки. Команда не создаёт OAuth-приложение или бота,
не меняет `adapter_mode`/`enabled` и не проверяет аккаунт внешним запросом.

`variants` создаёт записи для уже сохранённого Draft и включённых адресатов
его профиля. Это локальная подготовка вариантов, а не сбор источников, вызов
переводчика, согласование или отправка. Затем каждая версия проходит собственные
preflight и согласование точного адресата и даты.

`create-original` сохраняет собственный текст оператора для одного нового
прямого маршрута Telegram, VK API/браузер или Пикабу. MAX и прежние маршруты
этим способом не принимаются. Сначала настройте окончательный адресат,
включите его и профиль, выберите режим профиля кроме `dry_run`; адресат можно
оставить на паузе. Изменение binding после создания требует отдельного
пересмотра, а повторное создание того же текста для этого адресата блокируется.
Команда сама не включает профиль или адресат и не снимает паузу.

Входной UTF-8 JSON находится внутри копии, например в игнорируемом `data/`.
Он содержит ровно четыре поля, без URL загрузки и служебных policy-полей:

```json
{
  "title": "Заголовок собственного материала",
  "body": "Полный русский текст оператора без сокращений.",
  "media": [],
  "metadata": {}
}
```

Допускается одно локальное JPEG/PNG: `media` содержит объект
`{"path":"data/media/original.jpg","mime":"image/jpeg","sha256":"<64 строчных hex-символа SHA-256 оригинальных байтов>"}`.
Для Пикабу явно укажите точные `metadata`, например
`{"tags":["Наука","Контент нейросетей"],"community":"","ai_generated":true}`;
CLI не добавляет теги незаметно и отклоняет набор, который браузерный маршрут
нормализовал бы иначе. У остальных маршрутов допустимо пустое `metadata`.
Вход ограничен 1 МБ; ссылки и выход за корень копии запрещены.

`--attest-original` означает подтверждение оператором собственных прав на
точные title/body/media. Это отдельный аудируемый `owner-original-v1`,
с каноническими Story/Draft/revision/Variant, без подмены старого bridge-gate
или прав источника. Оно не является машинной проверкой или согласованием
публикации. Ответ содержит ID и hashes, без полного текста; approval,
dispatch и внешних действий команда не создаёт. После сохранения нужны
обычные preflight, просмотр полного текста/изображения и отдельное явное
согласование версии, адресата и даты. Изменение текста, изображения или
канонической истории делает исходное подтверждение непригодным.

`dispatch-once` обрабатывает уже согласованные и наступившие отправки.
`worker` повторяет проходы, но не создаёт статьи, не собирает источники, не
вызывает модели и не одобряет новые тексты. Запуск в текущей консоли допускается
только после проверки всех настроек копии и готовых согласований:

```powershell
.\scripts\start-four-platform.ps1 -Worker -ConfigurationReviewed -Interval 5
```

Без `-Worker` сценарий ограничивается guarded status и краткой таблицей без
секретов, адресов БД и полных текстов. `-ConfigurationReviewed` — явное
подтверждение проверки конфигурации оператором, не согласование публикаций.
Никакого автоматического включения, снятия пауз, нового approval или повтора
unknown он не выполняет. Остановка worker — `Ctrl+C`; журнал отправки не
удаляется. Для неподтверждённого внешнего исхода используется `reconcile`,
даже если ID потерян в БД, но сохранился в локальном журнале.

Нужны уже подготовленные Variants и их доказательства качества. Этот worker
не переносит автоматический научный сборщик на новые площадки. Генерация,
перевод и будущие отдельные политики новых маршрутов требуют своей настройки
и приёмки, сохраняя прежние ограничения `AGENTS.md`.

## Postiz и локальные проверки

В owner-панель добавлены каналы, проверка доступа, pause/resume, полный текст
черновика, просмотр изображения, preflight, дата по Москве и checkbox, который отмечает только человек.
Изменение версии, адресата или даты сбрасывает согласие. BFF принимает только
перечисленные route actions над сохранёнными ID и проверяет owner cookie,
организацию, Origin и exact envelope. Общей команды «опубликовать произвольный
текст/URL» нет. Внутренний BFF по умолчанию сохраняет рабочий порт `8092`.
Для отдельной копии разрешён только второй заранее определённый порт `18092`,
причём он выбирается явно в окружении **её** Postiz:

```dotenv
EDITORIAL_INTERNAL_PORT=18092
EDITORIAL_INTERNAL_URL=http://host.docker.internal:18092/internal/editorial
```

Без этого выбора URL на `18092` отклоняется. Другие порты, внешние hosts,
credentials/query/fragment в URL и другой путь запрещены; owner cookie,
организация, Origin и внутренний ключ проверяются как прежде. Публичный
Postiz копии остаётся на собственном loopback `14007`. Эти значения не
применяются к рабочему стеку исходного проекта.

Кнопка «Показать изображение» выполняет read-only action
`{"action":"preview","id":"<VARIANT_ID>"}` через тот же защищённый BFF.
Сервер проверяет SHA локального исходника и возвращает JPEG thumbnail,
связанную с exact `variant_id`, revision и `content_hash`, без upload или API
площадки. Ответ ограничен 1 МБ. `sha256` относится к исходным байтам, а не к
уменьшенному JPEG; на площадку отправляется исходный файл версии. UI принимает
только ограниченный `data:image/jpeg;base64,...`, отклоняя произвольные URL и
устаревшую версию. Для материала с изображением перед checkbox требуется его
просмотр; сам preview не выполняет preflight, не ставит checkbox и не создаёт
согласование. Отдельного CLI-подкомандного `preview` сейчас нет.

Почасовые записи с `manual_approval_allowed=false` остаются вне ручной формы:
для них не появляется checkbox или кнопка owner approval. Их автоматическая
политика и история остаются в прежнем разделе MAX.

История отправок использует сохранённую классификацию доказательств аудита,
а не текущий режим адресата: fixture остаётся «Локальная проверка» даже после
перевода адресата на live. API-квитанция и независимый readback имеют отдельные
подписи; без новых доказательств прежний verified-флаг обозначается только
как историческая запись. Подпись адресата берётся только из dispatch snapshot;
если историческое назначение не сохранено, UI сообщает об этом без подстановки
текущего адресата. Приватные объекты аудита в UI не передаются.

UI/BFF прошли 67 локальных Node/UI проверок со strict semantic TypeScript. Более ранний
layout fixture отдельно просмотрен на desktop/mobile; это не новая визуальная
приёмка последних подписей истории и не полный запуск Postiz. Локальный Docker daemon
недоступен; отдельный работающий стек Postiz этой копии и его браузерная
интеграция не подтверждены. Рабочая панель исходного проекта не заменяется.

```powershell
# Только локальные transport/Hub/isolation fixtures, Ruff и pip check.
.\scripts\test-four-platform.ps1
# Весь pytest, включая отдельную собственную PostgreSQL test DB.
.\scripts\test-four-platform.ps1 -Full
# Дополнительно существующие read-only TypeScript/React tooling и Node UI tests.
.\scripts\test-four-platform.ps1 -Full -Ui -EditorialTooling '<ПУТЬ_К_NODE_MODULES>'
```

Сценарий проверяет конечные пути `.test-state` и basetemp, отклоняет ссылки
и создаёт родительский каталог до pytest. Он не импортирует dotenv целиком,
удаляет унаследованный `DATABASE_URL` из дочернего процесса и берёт только
`TEST_DATABASE_URL` из `.env.local` этой копии. Разрешены loopback, порт `55448`
и БД `editorial_hub_tests`; другая БД отклоняется до запуска тестов. Для `-Full`
этот DSN обязателен. PostgreSQL-тесты используют отдельные случайные схемы;
runtime schema не подменяет тестовую. Секреты не передаются аргументами и не
печатаются. Отчёты остаются в игнорируемом `.test-state`.

Проверки не запускают worker, приёмку аккаунтов, сборщик или модели. Перед
живой эксплуатацией остаются отдельные доступы, живая приёмка цикла Пикабу, exact
публикации в разрешённые тестовые адресаты и работа собственного Postiz-стека.
API receipt, конфигурация, доступ, fixture и независимая доставка сохраняют
разные статусы.

`AGENTS.md` и прежние записи `CHANGELOG.md` остаются в истории без переписывания.
Архив исходников должен сохранять эти файлы, `prompts/` и согласованные версии
в `pyproject.toml`/`src/max_postiz_agent/__init__.py`. В архив и Git не входят
`.env.local`, profiles/cookies, установщики, Docker volumes, `data/`,
`.test-state` и runtime-отчёты с частными данными.
