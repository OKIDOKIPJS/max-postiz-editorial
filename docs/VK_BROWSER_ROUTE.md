# Отдельный браузерный маршрут VK

`vk_browser` — дополнительный транспорт к `vk_api`, с отдельным пользовательским
профилем и проверкой фактической записи. Он не использует токены VK ID,
недокументированные API, экспорт cookies или сессию встроенного браузера Codex.

Причина отдельного маршрута: в [отчёте upstream Postiz #1408](https://github.com/gitroomhq/postiz-app/issues/1408)
описано, что успешный вход через VK ID ещё не означает доступ к `wall.post` и
загрузке фотографий. Это отчёт другого пользователя, не проверка текущего
аккаунта. API-маршрут и его проверки сохраняются; обходы получения старых или
чужих токенов не добавлены.

## Текущее состояние

Код и локальный Playwright/HTTP fixture позволяют проверить полный цикл:
открытие редактора, полный текст, одно изображение, «Далее», финальная проверка,
один publish click и два независимых чтения стены. Fixture всегда сохраняет
`verified=false`; его журнал нельзя превратить в живое подтверждение.

**Живая публикация этим маршрутом не подтверждена.** На 31 октября 2026 агент
прочитал профиль, первый экран редактора и финальные настройки с подготовленным
частным черновиком без отправки в авторизованной вкладке с разрешения владельца.
Согласование точного текста, адресата и даты владельцем ещё ожидается;
публикация не выполнялась. Это наблюдение интерфейса, не согласование отправки.
Наблюдались:

- account: `[data-testid="header-profile-menu-button"]` с каноническим `href`;
- открытие: `[data-testid="posting_create_post_button"]`;
- текст: `[data-testid="posting_base_screen_input_message"]`, публичный
  `contenteditable`;
- файл: `[data-testid="posting_base_screen_download_from_device"]`;
- переход: `[data-testid="posting_base_screen_next"]`, «Далее»;
- контейнер записи: `[data-testid="post"]`, текст `[data-testid="post_text"]`
  и permalink `[data-testid="post_date_block_preview"]`; ссылка автора —
  `[data-testid="post-header-title"]`.
- финальная форма `[role="dialog"][data-testid="posting_modal_box"]`,
  preview `[data-testid="showmoretext-in"]`, publish
  `[data-testid="posting_submit_button"]` с надписью «Опубликовать»;
- ячейки соавторов `[data-testid="posting_coowners_cell"]` и видимости
  `[data-testid="posting_settings_visibility"]`; Story switch
  `[data-testid="posting_settings_repost_to_story_switch"]`.

Отдельных recipient/author anchors в финальных настройках личной стены нет.
Селекторы загрузки и финальной сверки изображения этим наблюдением не
подтверждены. Без полного явно проверенного DOM-контракта
preflight возвращает `VK_BROWSER_DOM_CONTRACT_UNVERIFIED` до открытия браузера,
загрузки изображения и согласования отправки.

## Подключение владельцем

Настройки задаются только в локальной конфигурации тестовой копии. Новый адресат
изначально выключен и на паузе. `owner` — положительный числовой ID вошедшего
аккаунта в строковом виде. `destination` — тот же положительный ID для своей
стены либо отрицательный ID сообщества. Канонические адреса фиксированы:
`https://vk.ru/id<ID>` и `https://vk.ru/club<ID>`.

Профиль по умолчанию — `data/vk-browser`; допустим отдельный
`data/vk-browser-<suffix>`. Чужие каталоги, ссылки/junction и общий профиль MAX
не используются. Команда login открывает отдельное окно для обычного входа
владельца. Она не переносит cookies из IAB, не получает API-токен и не публикует.

`dom_contract_verified` остаётся `false`, пока владелец не проверил полный
нативный редактор для конкретной стены и настройки. Действия с черновиком
требуют отдельного разрешения владельца. Наличие открытой сессии, подготовка
и просмотр черновика не заменяют явного согласования внешней отправки точного
текста, адресата и даты либо разрешения загрузки изображения.

Для изображений дополнительно обязателен `media_contract_verified=true`.
По умолчанию он false: даже успешный живой text-only тест не включает upload
фотографии. До отдельной проверки image-потока с разрешённым снимком preflight
возвращает `VK_BROWSER_MEDIA_CONTRACT_UNVERIFIED` перед editor/upload и созданием
журнала. Этот флаг не отменяет проверки байтов, SHA, прав и точного readback.

Полный `dom_contract` включает наблюдённые элементы выше и следующие ключи:

| Ключ | Что должен однозначно показывать |
| --- | --- |
| `wall_ready` | Загруженную стену до выбора новых записей |
| `uploaded_images` | Только загруженное фото текущего редактора |
| `recipient` | Видимого адресата с каноническим `href` или точным signed `data-owner-id` |
| `preview_author` | Видимую выбранную identity автора до отправки |
| `preview_text`, `preview_images` | Полный текст и фото после «Далее» |
| `publish` | Единственную видимую и доступную финальную кнопку |
| `publish_label` | Точную надпись кнопки; это строка, а не CSS-selector |
| `forbidden_settings` | Активные несогласованные режимы публикации |
| `extra_attachments` | Несогласованные вложения редактора |
| `post_images`, `post_extra_attachments` | Фото и лишние вложения внутри одной записи стены |
| `post_author` | Видимого автора конкретной записи; наблюдённый default указан выше |
| `blocked`, `errors` | Видимую проверку доступа/CAPTCHA и ошибки редактора |

Selectors относятся к видимому DOM; объекты фреймворка, приватные endpoints и
скрытые cookie/storage не читаются. Успешный inspect означает только проверку
доступа, с `live_verified=false`.

Адресат стены и автор записи проверяются независимо. Для своей стены автором
должен быть `owner`; для стены сообщества — само сообщество (`destination`).
Публикация от личного имени администратора в сообществе этим контрактом не
разрешается. Идентичность автора подтверждается видимой канонической ссылкой
`/id<ID>` или `/club<ID>`. Если интерфейс показывает vanity URL, нужен отдельно
проверенный `author_id_attribute` в DOM-контракте — имя публичного `data-*`
атрибута того же видимого элемента с точным числовым ID. Без этого публикация
блокируется; ID из скрытого состояния приложения не извлекается. Предварительный
`preview_author` для живого интерфейса сообществ пока не подтверждён.

У ссылки автора конкретного поста наблюдён служебный query `trackcode`.
Только для author href допускается ровно один непустой `trackcode` из ASCII
букв, цифр, `_` и `-`. Он не меняет проверяемый числовой path. Остальные query,
fragment, чужой origin и схемы вроде `javascript:` блокируются; account,
recipient и permalink сохраняют запрет query.

Внутри текста preview и опубликованной записи каждый anchor проверяется
отдельно. Его target обязан точно совпадать с HTTP(S) URL, явно присутствующим
в согласованном полном тексте или frozen `sources`. Ссылка на обычном слове
на посторонний адрес, `javascript:`, пустой href и неизвестный redirect блокируют
отправку либо оставляют readback unknown. Author/permalink вне текстового
контейнера этим правилом не подменяются. Redirect VK не распаковывается без
отдельного проверенного контракта; переписывание URL интерфейсом может
потребовать явной доработки. Список targets входит в каждый captured snapshot
и оба receipt reload: один SHA видимого текста не доказывает правильность ссылок.

Для своей положительной стены доступен отдельный явный контракт
`dom_contract.identity_contract="personal-wall-settings-v1"` вместе с
`text_contract="vk-spacer-div-v1"`. Только в нём `recipient` и `preview_author`
заменяются одновременной проверкой точного URL своей стены, числового account ID,
открытия нового пустого composer известной кнопкой и финальных настроек. Для
сообщества этот режим отвергается ещё локальным preflight; прежний explicit-v1
требует собственные доказанные recipient/author элементы.

Личный контракт требует видимую форму «Форма постинга», пустую ячейку
«Пригласить соавторов» без ссылок и видимость «Кто увидит этот пост / Все».
Другие включённые checkbox/radio/switch блокируют отправку. Native Story switch
в наблюдённом интерфейсе был включён по умолчанию. Worker сначала фиксирует
`story_disable_intent` с fsync, снова проверяет approval/lease/account/settings,
выключает его штатным checkbox и проверяет `checked=false` и согласованный
`aria-checked` перед click. Если выключить не удалось либо он включился снова,
публикации нет. `sender_settings.story_checked=false` подтверждает эту настройку
отправителя; проверка стены сама по себе не доказывает отсутствие отдельной
Story во всём аккаунте.

Native preview вставляет пустой spacing DIV с одним BR между абзацами.
`vk-spacer-div-v1` переводит только эту проверенную структуру в два перевода
строки. Block wrappers допустимы только как одна unary цепочка до content;
соседние block DIV, `display:block` у inline элементов и скрытый BR блокируются.
Он не схлопывает остальные пробелы/переводы строк и блокирует скрытый
или неподтверждённый DOM. Перед click весь scoped DOM проверяется на лишние
изображения, видео, аудио, iframe, файлы и вложения; изображение должно быть
тем же элементом, что участвует в проверке SHA. Успех text-only не включает
`media_contract_verified` и не подтверждает живой image-контракт.

## Точная версия и единственная попытка

Транспорт сохраняет весь заголовок и текст без обрезки и без буквальных
Markdown-звёздочек. Заголовок обычный: нативный жирный текст VK не заявляется.
Уже включённый в тело заголовок не дублируется. Предел — 16384 единицы UTF-16,
допускается одно проверенное JPEG/PNG до 10 MiB.

Для внешней отправки владелец явно согласует snapshot с текстом, фото,
адресатом и датой; агент сохраняет это решение. Автоматическая политика MAX
не согласует новые VK-публикации. Браузерный worker
повторно проверяет `sending`, первоначального владельца lease, запас времени,
неизменные approval/snapshot/options, дату и паузу перед изменениями редактора,
загрузкой, «Далее» и Send. Проверка выполняется снова после ожиданий и чтения
изображения. Транзакция БД не удерживается во время HTTP или браузерного действия.

`data/vk-browser-operations/<request_id>.json` — закрытый runtime-журнал с
эксклюзивным claim и fsync до внешних изменений. В нём связаны точные root,
request ID, destination, snapshot/options/DOM hashes, фазы и известный permalink.
Редакторский upload и финальный click выполняются по одному разу. Потеря ответа,
lease, неизвестный результат или сбой сохранения не разрешают повтор.

После click требуется ровно одна видимая запись с каноническим wall ID,
полным точным текстом, правильным адресатом и фото; затем стена читается заново
дважды. При каждом чтении полный snapshot записи, URL/число изображений,
дополнительные вложения, аккаунт и контекст стены проверяются повторно после
загрузки байтов изображения. Замена DOM во время HTTP не подтверждает старое
фото новым состоянием страницы. Проверяются также отсутствие дополнительных
вложений и SHA изображения.
Если VK преобразует байты изображения и исходный SHA больше не подтверждается,
результат остаётся заблокированным/unknown; проверка не ослабляется автоматически.

Известный ID сохраняется до readback. Отдельный reconcile выполняет только
чтение этой записи и два свежих чтения стены, даже если локальный журнал ранее
содержал confirmed. Прежний proof хранит результат прошлой проверки;
fixture всегда остаётся локальной проверкой без живого подтверждения.
При удалённом или изменённом посте прежнее доказательство сохраняется как
`historical_proof`, а текущая проверка остаётся unknown. Время `observed_at`
относится к фактическому чтению.
Ответ worker дополнительно проверяется на границе адаптера: оба reload должны
содержать SHA полного согласованного текста, точный список SHA изображений,
полную author proof, правильный permalink и typed proof. Для reconcile план
строится из переданного frozen DB snapshot, который обязан совпадать с sealed
журналом и точными options/destination; совпадения
одного wall ID или верхнего snapshot hash недостаточно для confirmed.
Confirmed stdout дополнительно сравнивается с перечитанным после worker
sealed журналом: ID, URL, proof, clicks и durable fixture marker совпадают.
Fixture marker нельзя заменить в stdout на live. Timestamp обязан относиться
к текущему reconcile, лежать после создания журнала и не в будущем; старое
доказательство не выдаётся за свежую сверку. Без DB snapshot reconcile остаётся
unknown до запуска worker.
Без известного ID исход остаётся unknown. Повторный вызов
publish с тем же request ID не открывает новый редактор, не загружает фото и
не нажимает кнопку повторно. Все приватные snapshots, журналы и данные профиля
остаются в игнорируемом `data/`; в исходники и отчёты с публичным доступом они
не включаются.
