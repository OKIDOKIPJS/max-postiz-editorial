# Четыре маршрута 0.12.1: установка и эксплуатация

1 ноября 2026, Europe/Moscow. Версия подготовлена в отдельной копии;
рабочий сервер этим релизом не обновлялся. Проверки кода,
готовность локальной конфигурации, доступ к аккаунту и фактическая доставка —
разные результаты. Итог проверки кода и живая приёмка приведены ниже;
контрольные суммы поставляемых архивов записываются в release-verification.json.
Исторический протокол 0.12.0 сохранён в `FOUR_PLATFORM_ACCEPTANCE.md`.

## Установка новой копии

Нужны Python 3.12, собственный `.venv` и Google Chrome для браузерных маршрутов.
`SourceRoot` обозначает исходный checkout, который копия не должна изменять.
Проверка `-Check`/`--check` не устанавливает пакеты и не запускает службы.

```powershell
pwsh -File scripts/install-four-platform.ps1 -SourceRoot '<ИСТОЧНИК>' -Check
pwsh -File scripts/install-four-platform.ps1 -SourceRoot '<ИСТОЧНИК>' -Browser
.\.venv\Scripts\python.exe -m max_postiz_agent.routes_cli --root . doctor
.\scripts\start-four-platform.ps1
```

```sh
bash scripts/install-four-platform.sh --source-root '<ИСТОЧНИК>' --check
bash scripts/install-four-platform.sh --source-root '<ИСТОЧНИК>' --browser
```

Установщик создаёт выключенные адресаты и локальные секреты. Он не входит в
аккаунты, не включает источники, не запускает модели, worker или Docker.
Флаг `-Browser` / `--browser` устанавливает Python-зависимости браузерных
маршрутов; сам Google Chrome должен быть установлен отдельно. Без этого флага
браузерные зависимости не устанавливаются.
`doctor` читает только локальные предпосылки: наличие credentials, собственных
профилей и полного DOM-контракта. БД, lease, согласования, качество, доступ и
доставка этим вызовом не проверяются. Значения секретов и адресаты не выводятся.
`production_ready=false` не заменяется успешным входом.

Для runtime используется собственный PostgreSQL; настройка loopback-копии
описана в `FOUR_PLATFORM_ROUTES.md`. Профили браузеров и авторизация остаются
в игнорируемом `data`, токены вводятся локально через `set-token`.

## Браузерный runtime VK и Пикабу

Описанные ниже Job/cgroup supervisor, parent generation и свежие финальные
SQL fences относятся к VK и Пикабу. MAX сохраняет прежний browser transport
с собственным `browser_publisher.py`; его механизм запуска этим релизом не менялся.

Windows worker до передачи запроса помещается в собственный Job с
KILL_ON_JOB_CLOSE. Таймаут и прерывание завершают только его дерево процессов.
Chrome не должен оставаться держать профиль после завершения worker.
Реальная проверка Windows выполнена на отдельных процессах и Chromium;
модель Job описана в [документации Microsoft](https://learn.microsoft.com/windows/win32/procthread/job-objects).

На Linux нужен cgroup v2 с `cgroup.kill` (Linux 5.14+) и делегированная
не корневая cgroup службы. Источник `max-postiz-editorial.service` содержит
`Delegate=yes`; работающая служба владельца не изменялась. До передачи stdin
worker получает отдельную приватную cgroup, которую fork/setsid не покидают.
Без делегации запуск браузерной операции отклоняется. `doctor` проверяет только
доступные read-only признаки и не заявляет выполненное создание/cleanup.
Живой Linux kernel/Chromium cleanup на этой Windows-машине не проверялся.

Длительные проверки содержимого завершаются до последней свежей SQL-проверки
lease, паузы, approval и binding. Native действие выполняется в пределах
секундного окна с повторным атомарным чтением DOM. Это ограничивает окно
авторизации, но не является общей транзакцией БД и стороннего сайта.
После native переходов VK отдельно ожидает появление редактора, готовность
«Далее» и согласованное состояние checked/aria у Story. Эти ожидания только
читают UI; каждое следующее изменение по-прежнему проходит свежие проверки.
При проверке доставки готовая шапка и кнопка редактора не означают, что список
постов уже загружен. На каждой из двух независимых загрузок стены предусмотрено
ограниченное ожидание точного поста. Оно не заменяет последующую строгую сверку:
неверный ID, дубли, аккаунт, автор, текст, ссылки и вложения сохраняют блокировку.

Изменение app/topic/publishing или `.env.local` требует актуального процесса.
Старый worker останавливается до claim, сохраняет новые approvals и не
использует старый cached token после смены credentials. Браузерный дочерний
процесс проверяет поколение родителя до SQL и открытия профиля.
Переменная, уже заданная окружением службы, имеет приоритет перед `.env.local`.
При ротации обновляют выбранный источник credentials и перезапускают только
собственный процесс; вход в браузер или изменение файла не заменяют эту проверку.

## Форматы и согласование

- MAX сохраняет прежний transport, политику и ограничения. Новые маршруты
  не получают автоматическое согласование научной политики MAX.
- Telegram использует Bot API: текст, настоящее жирное начертание заголовка,
  опциональное фото и durable шаги. API receipt остаётся `verified=false`:
  самостоятельного `getMessage` readback у этого адаптера нет.
- Личная стена VK выбирает `dom_contract_profile="personal-text-v1"`.
  Полный контракт поставляется с кодом, но `dom_contract_verified` в примерах
  выключен. Нативный текстовый renderer `vk-native-text-v2` учитывает
  наблюдённые inline/flow-root wrappers и spacing BR. Сравнивается полный
  логический текст DOM; стандартное свёрнутое превью не выдаётся за просмотр
  всех строк на экране. Скрытые узлы/BR и неизвестные границы блоков запрещены.
  Поиск сначала исключает заведомо другой текст старых записей; возможное
  совпадение, включая raw DOM со скрытыми вставками, сохраняет строгие проверки.
  Story выключается штатной видимой меткой переключателя; checkbox и aria
  проверяются повторно. Пресет не принимает media даже при случайной смене
  отдельного media-флага. Заголовок VK остаётся обычным текстом.
- Пикабу автоматически заполняет заголовок, тело и точные теги, делает один
  Publish и проверяет результат. Неоднозначный завершающий перевод строки
  отклоняется без обрезания текста. Изображения остаются отдельным закрытым
  контрактом до их живой приёмки.
  Авторские теги сравниваются точно. Отдельное versioned правило допускает
  только автоматически добавленный площадкой форматный «Текст» при media=[];
  declared и effective tags/hash сохраняются отдельно. Остальные дополнительные,
  пропущенные и повторные теги блокируют подтверждение. Это поведение описано
  в [официальной справке](https://help.pikabu.ru/article/39889).

Полный текст, media, источники и posting metadata загружаются в Postiz отдельным
read-only `details` для точной revision/content hash. До этого формы approval
нет. Инвентарь разбит на страницы по 50; старые неизвестные исходы доступны
через фильтр незавершённых отправок. Поля не обрезаются молча при превышении
лимита ответа. CLI также поддерживает `details <VARIANT_ID>` без quality/отправки.

После подготовки выполняются `preflight`, точное согласование будущей даты и
один `dispatch-once`. `worker` обслуживает только готовые согласования.
Изменение версии/даты/адресата/metadata сбрасывает прежнее решение.
Автоматический выбор времени допустим только внутри отдельного явного
поручения владельца; выбранная точная дата всё равно сохраняется в approval.

## Неизвестные исходы и обновление

При expiry sender теряет полномочия, а отправка остаётся `unknown`.
Read-only `reconcile` доступен и при общей паузе. Поздняя квитанция сохраняется
как доказательство, но сама не повышает unknown до published/verified.
Живой lease не сбрасывается; повтор Publish/HTTP для unknown запрещён.
Удаление уже созданного поста площадкой не разрешает его повторную отправку.
Для VK один старый запрос отдельно закрыт как доказанно не отправленный:
валидный журнал с Publish-intent=0 связан с точной frozen версией worker,
закрытым процессом, неизменным approval и двумя загрузками стены. Этот частный
протокол не является общей автоматической амнистией старых unknown journals.
Новые журналы дополнительно записывают startup worker SHA и последний action
intent; само наличие clicks=0 без проверенного происхождения недостаточно.

Перед обновлением сохранить собственные БД, локальные конфиги, профили и журналы;
проверить sending/unknown/lease, остановить только свой worker. Исходный архив
не заменяет такой приватный backup. После смены credentials/code нужен новый
процесс. История approvals, claims, journal и прежние отказы не переписываются.
При откате неизвестный внешний исход не повторяется даже старой версией.

## Новый Postiz image

```sh
node deployment/postiz-max/build-production-image.cjs --check
node deployment/postiz-max/build-production-image.cjs --build --origin http://<host>:14007 --tag max-postiz-linux:0.12.1-production-<unique>
```

Новый recipe начинается с pinned official OCI, включает текущие MAX provider/
guard и editorial source overlay, затем пересобирает backend, orchestrator и
frontend. Он не зависит от старого локального image 0.5.1 или его compiled API.
`--check` проверяет только структуру; `--source-root` дополнительно проверяет
13 закреплённых upstream SHA. `--build` отказывает при занятом tag, удалённых
Docker/Buildx overrides и использует проверенный локальный context/default builder.
Контейнеры, volumes, compose, push и deployment этот runner не меняет.

Docker daemon на машине проверки недоступен: полный Next/image build и запуск
нового стека **NOT_BUILT / NOT_STARTED**. Отдельная semantic-проверка overlay с
настоящими TS/Nest/React types не подменяет эту приёмку. Legacy Postiz-команды
отказывают в копии с isolation marker, чтобы не управлять старым compose-проектом.

## Проверки

`scripts/test-four-platform.ps1 -Full -Ui` включает весь pytest, собственную
PostgreSQL test DB, Ruff, pip check, UI и production-build contracts.
Перед проверками Python отдельно устанавливают dev-зависимости в `.venv`:

```powershell
.\.venv\Scripts\python.exe -m pip --isolated install --index-url https://pypi.org/simple -r requirements-dev.lock
```

Для `-Ui` нужны Node и отдельные `node_modules` с TypeScript 5.5.4, React и
React DOM 19.2.4, `@types/react` 19.1.8, `@types/react-dom` 19.1.6 и
`@types/node` 18.16.9. Это проверенный набор версий инструментов QA:

```powershell
npm install --registry=https://registry.npmjs.org --prefix data/postiz-editorial-tooling --no-save --ignore-scripts typescript@5.5.4 react@19.2.4 react-dom@19.2.4 @types/react@19.1.8 @types/react-dom@19.1.6 @types/node@18.16.9
```

Путь передаётся через `-EditorialTooling '<путь к node_modules>'`
либо `EDITORIAL_TOOLING`; по умолчанию используется игнорируемый
`data/postiz-editorial-tooling/node_modules`. Runtime-установщик эти инструменты
QA не устанавливает. `TEST_DATABASE_URL` задаётся только для своей тестовой БД;
порядок настройки приведён в `FOUR_PLATFORM_ROUTES.md`.

Финальный полный frozen-прогон: **6018 passed, 1 failed, 8 skipped, 2 warnings**,
3562.04 с, 550 файлов без изменения исполняемого кода. Единственный отказ —
положительный fixture-тест author tracking VK: секундное окно авторизации
истекло до открытия редактора, Publish-intent=0 и external_id отсутствует.
На том же неизменном коде этот тест, строгие отрицательные проверки ссылок,
автора, паузы и медленной авторизации прошли отдельно: **15 passed, 1 warning**,
11.25 с. Приёмка фиксируется как полный прогон плюс эта перепроверка:
**6019 уникальных passed**, исходный failed-отчёт сохранён.

Восемь пропусков: четыре проверки symlink без привилегии Windows, две native
Linux cgroup/setsid и две Linux pipe. Обе проверки sender/recovery на собственной
PostgreSQL test DB прошли. Отдельно прошли 259 тестов VK, 81 Node UI/build
contract, Ruff и pip check; наборы пересекаются и не суммируются. Partial semantic
проверка с настоящими TS/Nest/React types дала 0 diagnostics и сверила 13 upstream
pins; полный Next/image build остаётся NOT_BUILT.

Fixture/HTTP receipt/offline DOM, доступ и реальная доставка сохраняют отдельные
статусы. Полные приватные журналы тестов и публикаций в исходный архив не входят.

## Живая приёмка копии 1 ноября

Датированный результат этой копии; идентификаторы, профили, полный текст и
приватные доказательства остаются в игнорируемых локальных файлах.

- MAX: прежний transport сохранён; новой живой отправки в этой копии не было.
- Telegram: один пост принят API и отдельно прочитан в закрытом тестовом канале
  с точным текстом и жирным заголовком. API receipt сохраняет `verified=false`;
  независимое наблюдение записывается отдельно.
- VK: один пост создан и виден на личной стене с точным текстом без изображения.
  После исправления ожидания загрузки штатная read-only сверка дважды прочитала
  стену и подтвердила `published, verified=true`. Сохранены одна попытка и один
  Publish; новый approval и повторная отправка для сверки не создавались.
- Пикабу: единственный тестовый пост был создан, затем площадка удалила его
  с причиной «Флуд». Текущий dispatch остаётся `unknown`, адресат на паузе;
  новых публикаций и попыток обхода модерации не было. Исторический capture
  не является подтверждением доступной сейчас записи.
